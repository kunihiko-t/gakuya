# gakuya 次の版：その場で照明を調整する 設計

- 日付：2026-11-06
- 状態：実装して本体の Unity で通した。音と操作感はユーザーの確認待ち（確認の前に、ユーザーの指示で実装まで進めた。コミットはしていない）

## 何のためか

動画レビューでは「このあたりへん」と伝えられるようになったが、照明は直しては書き出すことの繰り返しのままである。ユーザーが直したいのは、光の色、暗すぎる、明るすぎる、肌への反射が明るすぎる、服の反射がサテン生地のようで安っぽい、布なのに金属のように光る、といった見え方である。これらは言葉だけでは加減を伝えにくい。

ユーザーは「再生中のライティングが本番と異なると実際のライトがわからない」と言っている。ブラウザで別に描いた近似では判断できないので、**本番と同じ描画の絵を見ながら、つまみで加減を決める**。「なるべく Unity の絵に寄せたいけど、無理そうならそれでもいい」とも言っているが、試作では本番の合成を GPU に移して全画素で最大1〜2段階（255段階中）の差に収まったので、寄せる方針で進める。

カメラの回転は扱わない。ユーザーが「じゃあカメラはやめとくか」と決めた。

## 利用の流れ

ユーザーの言葉は次のとおり。

> AI がつまみを出して、そこを動かすと色や明るさが変わって、任意のところでこのぐらいって伝えるとかできたら楽。照明の雰囲気をガッツリ変えたい時は別にスライダーとかなしで会話で変えていい。

これを次の流れにする。

1. **人が言う：** 「服がサテンっぽい」と会話で言う。動画レビューの指摘でもよい。
2. **AI がつまみを出す：** その話に合うつまみを gakuya の画面に出す。つまみの種類は固定しない。
3. **動かすと絵が変わる：** 本番と同じ描画の絵が、音と一緒に流れたまま変わる。
4. **「このぐらい」と伝える：** 値と範囲が AI に届く。押すまで AI は設定を書き換えない。
5. **AI が照明の設定に書き込む：** 書き込んだあと、絵にも反映される。大きな変更はつまみなしで会話で行う。
6. **本番の書き出しで見比べる：** 今の `gakuya done` で前の版と並べて確かめる。

## 値の効く範囲

ユーザーの指定は次のとおり。

- **だいたい全場面に効かせる：** 服の光沢、キャラクターの明るさ。
- **タイムラインの範囲で指定する：** 光の色、場面の明るさ。「自然な感じに」反映する。変わり方は「曲による。テンポや拍に合わせて」。

範囲の指定は次のように動く。

- 範囲は、今のタイムラインのドラッグで選ぶ。
- 両端を近くの拍に吸い付かせる。拍は、今の動画レビューが音から求めた BPM と開始位置を使う。
- 変化の長さは秒ではなく拍の数で持つ（1拍でパッと、4拍かけてじわっと、など）。最初の値は AI が曲を見て提案し、違えば会話で直す。**この長さのつまみは作らない。**

## 目標

### 描画側につなぐ

- `gakuya <動画> --live <URL>` で、描画側（下の「描画側との約束」）につなぐ。動いているレビューには `gakuya live <URL>` でつなぐ。動画は最後に書き出したものを渡す。コマ数はこの動画から取り、音、拍、波形も、別の音を選ばない限りこの動画から取る。
- 描画側がまだ動いていなくても起動は失敗させず、応答がないことを画面に出して、動き出したらつながる。
- 動画レビューだけなら、今までどおり動画ファイルだけで使える。描画側がなくても動画レビューの機能は減らない。
- つないだときに描画側の fps とコマ数を確かめ、動画と違えば画面に出して進めない。範囲のコマ番号の意味が変わるため。

### ライブの絵

- 中央の絵を「動画」と「ライブ」で切り替える。配置（中央に絵、右に指摘と AI、下にタイムライン）は保つ。
- ライブでは、選んだ音を鳴らし、絵は描画側の時計で進む。絵は間に合う分だけ出し、間のコマは飛ばす。
- 再生、停止、シークはタイムラインから今と同じ操作でできる。
- 範囲を選んでいるあいだは、その範囲を繰り返す。
- 描画側が止まったら、古い絵を新しい絵のように見せず、応答がないことを画面に出す。

### 音の元

ユーザーの言葉は「音はshortと並べて再生することで鳴らせると嬉しい感はある。あとは音のファイル指定とか動画指定で音だけ使うとか」。動画だけのレビューでも、ライブでも同じように選べる。

- 画面の「音」で、この動画、見本（並べて再生している動画）、ファイルから選ぶ。起動時は `--audio <音声か動画のパス>` か `--audio reference`。
- ファイルには音声も動画も指定でき、動画は音だけを使う。絵は出さない。パスだけを覚え、コピーしない。
- 別の音を選ぶと動画は消音し、選んだ音を動画の時計に合わせて鳴らす。ズレは秒で指定する。見本の音は見本のズレを使う。ズレが負なら、音の始まりまで無音にする。
- 拍と波形は鳴っている音から取る。ただし手で決めたテンポと AI が決めたテンポは保つ（設計者の判断）。
- 読めない音は理由を画面に出し、動画の音に戻す。無音のままにしない。

### つまみ

- AI は `gakuya knobs --file <JSON>` でつまみを出す。何度でも入れ替えられ、画面はすぐに変わる。
- 1つのつまみが持つのは、ID、見出し、左端の値（`min`）、右端の値（`max`）、初期値、目盛り（線形か対数か）、効く範囲（全場面か、タイムラインの範囲か）である。右ほどぼけるつまみのように、`min` が `max` より大きくてもよい。「場面どおりに戻す」のような、値を外す操作も持てる。
- 描画側が知らない ID は `gakuya knobs` の時点で断る。動かしても変わらないつまみを出さないためである。新しい種類のつまみが要るときは、AI が描画側のコードに足してから出す。
- 動かすと、値がすぐ描画側に届く。値は設定を置き換える絶対の値で、倍率にしない（値を外すと設定どおりに戻る）。
- 範囲のつまみは、範囲を選んでいればその中だけで効き、選んでいなければ全編で仮に効く。全場面のつまみは、範囲を選んでいても全編で効く。範囲は繰り返し再生の区間でもあるので、サビを繰り返しながら全場面の光沢を決められる。

```json
[
  { "id": "gloss", "label": "服の光沢", "min": 0, "max": 3, "default": 1, "scale": "linear", "scope": "global" },
  { "id": "hue", "label": "光の色", "min": 0, "max": 360, "default": null, "scale": "linear", "scope": "range", "reset": "場面どおりに戻す" }
]
```

### 「このぐらい」

- 押すと、`gakuya wait` に新しい出来事 `settled` が届く。値、範囲、そのときのコマを含む。

```json
{ "event": { "type": "settled", "values": { "hue": 185, "level": 2 }, "frames": [480, 592], "frame": 486 } }
```

- `values` は今出ているつまみの全部で、値を外したつまみは `null` である。`frames` が効くのは範囲のつまみだけで、全場面のつまみは範囲を選んでいても全場面の値として届く。例外は会話で受ける。
- 届くのは、あわせて最後の動画のパスと、今のテンポ（BPM と開始位置）である。AI はこれで範囲と変化の拍数をコマに換算できる。
- AI は値を照明の設定に書き込み、`gakuya reload` で描画側に読み直させ、`gakuya knobs` でつまみを出し直す。全場面のつまみは書き込んだ値を初期値にし、範囲のつまみは `null` を初期値にする（範囲なしのとき値が全編に広がらないように）。つまみの値は出し直すまで残り、出し直すと、定義が同じでも初期値に戻る。gakuya は設定の中身を知らない。
- 範囲のつまみを範囲なしで押したら `frames` は省かれ、AI がどこに効かせるかを会話で確かめる。
- 「このぐらい」を押さずに範囲を選び直したら、つまみの値は新しい範囲についていく。
- つまみを動かしているあいだ、範囲の境では絵が急に切り替わる。拍数に合わせた変化が見えるのは、AI が設定に書き込んで読み直したあとである。

### AI の手順

同梱のスキル `skills/gakuya/SKILL.md` に、次の手順を足す。

- つまみを出す前に、**範囲全体を細かく動かして、絵が変わらない区間がないかを複数の場面で測る**。試作では、背景のぼけのつまみの右側約9割が、あるコマでまったく効いていなかった。値が効く範囲はコマによって違う。測るときは描画側の `/knobs` と `/frame` を AI が直接呼ぶ。人の絵も動くので、人がライブを見ていないときに行うか、先に断る。
- 効く範囲に合わせて最小と最大を決め、人の感覚に近い目盛りを選ぶ。
- 「このぐらい」が届くまで設定を書き換えない。
- 指摘から始まったときは今の流れのままで、「はい」のあとにつまみを出し、新しい書き出しを `gakuya done` で渡す。会話から始まって指摘がないときは、`gakuya render --video <動画>` で新しい版を渡す。どちらも前の版と並ぶ。

## 描画側との約束

gakuya は描画しない。描画側は、次の HTTP を `127.0.0.1` で提供する別のプログラムで、エンジンを問わない。gakuya はこの約束の文書（`docs/live-renderer.md`）と、テスト用の小さな偽の描画側（色を描いた JPEG を返す）だけを持つ。

| 呼び出し | 内容 |
|---|---|
| `GET /info` | fps、コマ数、幅、高さ、動かせるつまみの ID の一覧 |
| `GET /frame?after=<id>` | 新しい絵（JPEG）。ヘッダに絵の ID、曲のコマ番号、どのつまみの値までを反映したかの番号 |
| `POST /knobs` | 全場面の値、範囲の値、範囲、再生か停止か、シーク先、番号 |
| `POST /reload` | 照明の設定を読み直す |

画面から描画側へは、gakuya のサーバーを通して中継する。画面の出どころを今のトークンの確認の中に収めるためである。`--live` に渡せるのは手元のアドレスだけにする。

## 描画側の作業（このリポジトリの外）

手元の Unity プロジェクトの中に作る。個人の素材と同じ扱いで、このリポジトリには入れない。試作は使い捨てなので作り直す。残す場合はユーザーに改めて確認する。

- 本番の合成を GPU に移し、Editor の中の HTTP から JPEG を送る。作りは試作を参考にする。
- 照明の設定を、コードの中の表からファイルへ出す。全場面の値と、範囲ごとの色、明るさ、変化の拍数を持つ。今の表は10区間で、境で1コマのうちに切り替わる。
- 仮の値を本番の値に置き換える。試作の合成の引数の一部は本番の値を見つけられず、仮の値で動かしている。
- 本番の書き出しも同じ GPU の合成で行い、合成を一本にする。ライブと書き出しで同じ設定ファイルを読む。

## 試作でわかったこと

複製した Unity プロジェクトで、1080×1920、Editor の中から手元のブラウザへ送って測った。

| 項目 | 結果 |
|---|---|
| 流れる枚数 | 約14枚/秒（曲は30fps。間のコマは飛ぶ） |
| つまみから絵まで | 再生中は中央値128ms（90〜185ms）、停止中は92ms（83〜147ms） |
| 1枚の大きさ | 約200〜370KB |
| GPU 合成と CPU 合成の差 | 全画素で最大1〜2段階 |

ユーザーは、音を鳴らして約14枚/秒の絵で拍を確かめることに「そうだね」と答えた。「画質落として早く出来たりするならそれでもいい」とも言ったが、解像度を半分にしても約18枚/秒で頭打ちだった。上限を決めているのは解像度ではなく、描画の準備にかかる Unity 側の処理（約33ms）である。

つまみの効き方も確かめた。

- **光の色、場面の明るさ、服の光沢は大きく効く。** 服の光沢は 0 でマットな布、3 で金属のように光り、ユーザーの言う症状を両方向に再現できた。
- **場面の明るさは頭打ちになる。** 今は場面の明るさへの倍率で、上限1で切っている。本番では、倍率ではなく明るさそのものを動かす形にする。
- **肌だけを暗くすると崩れる。** 肌の材質の色を下げると顔の下側が灰色のマスクのようになり、原因はわかっていない。全身に倍率を掛ける形なら崩れない。
- ユーザーは「背景のボケ以外は変化が確認できました」と言った。絞りをそのまま動かすつまみは、どの目盛りにしても場面によって効かない区間が残る。ピント距離が場面で 2.3〜5.2m と違い、同じ絞りでも背景のぼけが2倍以上違うためである。下の「実物で通した結果」のとおり、ぼけの量（0〜1）を動かす形に直した。直したあとの操作感はまだ聞いていない。
- 今の合成は「くっきりした人物」を「ぼかした背景」に重ねるので、動かせるのは背景のぼけだけである。

## 実物で通した結果（2026-11-07）

複製の Unity を約束に合わせて、実際の曲の動画（1146コマ、30fps）で通した。AI が画面を操作し、音は実際に再生した。Mac はミュートなので誰も聞いていない。音が拍に合って感じられるかは、ユーザーの判断が要る。

- **本番との一致：** 7コマで同じ設定のライブの絵と書き出しを比べ、PSNR は 35〜38dB だった。同じ番号のコマが最も一致し（前後のコマは25dB以下）、番号はずれていない。並べた絵でも場面、姿勢、色味は同じに見える。ユーザーが見分けられないかは、まだ確かめていない。
- **流れる枚数：** 描画側だけで約18枚/秒、窓の前後で差はない。ページを通した全曲の再生で14.5枚/秒、最大間隔193ms。前回の約7枚/秒は再現せず、窓のせいでもなかった。別の書き出しやタブと重なっていたが、原因は確かめていない。
- **音と絵のずれ：** 音の時計に対する絵の遅れは、全曲の再生で約0.9コマ、途中からの再生で中央値1.5〜2.6コマ（50〜90ms）、範囲の繰り返しで約3.3コマ（約110ms）。広がり続けることはなかった。全曲の再生の終盤に一度だけ約5コマへの段差があり、別の再生では再現しなかった。
- **範囲の繰り返し：** 485〜590 が3.55秒ごとに戻り、音の止まりは最大33ms。
- **つまみの全範囲：** 服の光沢、キャラクターの明るさ、光の色、場面の明るさは全範囲で絵が変わった。背景のぼけは絞りをそのまま動かす形では、900、1120コマで右半分がほとんど効かず、120コマで左端の1割がまったく効かなかった。つまみをぼけの量（0〜1）にして、絞り＝6.5→2.3 を対数で動かしてピント距離で割る形に直すと、4場面とも形がそろい、隣の目盛りとの差が 0.24〜1.0（0〜255）に収まった。両端の絵も目で確かめた。左端でも、ピント距離の遠い場面（約5m）は絞り約1.25で、今の書き出し（絞り2）よりぼける。左端を広げると近い場面で効かない区間が増える。
- **範囲と拍：** 範囲を選ぶと拍に吸い付き（485〜590）、光の色は範囲の中だけで変わった。
- **「このぐらい」から設定まで：** `gakuya wait`、設定への書き込み、`gakuya reload`、つまみの出し直しまで通った。書き込む前と後で、範囲の中の絵の平均色は同じだった。範囲の前後は2拍かけて変わった。
- **描画側の再起動：** ライブ中に止めると「描画側が応答していません」が出て「このぐらい」が押せなくなり、立ち上げ直すと消える。動かしたつまみの値は送り直され、再起動後の絵は同じ値の絵と差が0だった。
- **ライブ中の指摘：** 映っているコマのスナップショットはライブの絵になる。範囲の他のコマは、ライブの絵がないので動画のままである。
- **未解決：** 別の書き出しと重なっていたあいだに一度、描画側の絵が約2分ほとんど届かない時間があった。書き出しが終わった後は再現せず、原因はわかっていない。「絵が届いていません」の表示は出た。

## 本体での結果（2026-11-07）

ユーザーの「別に本体変えていいよ」を受けて、本体の Unity プロジェクトに新しいファイルだけを足した（合成のスクリプトとシェーダー、照明の設定ファイル）。既存のファイルは変えず、シーンと設定はハッシュが同じままで、コミットもしていない。別のセッションが同じ作業フォルダにいるので、今の `LookTrial` 系の書き出しから切り替えるかは、そのセッションと合わせて決める。

- **4K の全編書き出し：** 2160×3840、1146コマを186秒で書き出した。CPU 版の約3.2秒／コマに対して約0.16秒／コマで、約20倍速い。本番の4K動画と比べて全コマ平均39.3dB、最低36.8dB（コマ322）で、最低のコマも並べると姿勢と色が同じに見えた。
- **ライブの絵と書き出し：** 1080×1920 のライブの絵と4Kを縮小した絵で 32.9〜36.8dB。姿勢と光は同じで、ドットの鋭さが違う。ユーザーが見分けられないかは、まだ確かめていない。
- **つまみの全範囲：** 本体の絵で、5種類を3場面、5目盛りずつ動かし、効かない区間がないことを確かめた。場面の明るさは 0 で暗い場面になり、スポットライトが点くので本人は暗くならない。
- **別の音での全曲再生：** 音のファイルを選んで全曲を通した。音と動画の時計のズレは最大0.043秒、絵の遅れは中央値1.3〜1.8コマ、最大2.7コマ、約16〜17枚/秒だった（画面なしの Chrome で、動画の時計と比べた）。隠れたペインで `viewer.frame` と比べたときは +34〜−23 コマに振れた。条件が2つ違うので、どちらのせいかは切り分けていない。
- **まだ人が聞いていないこと：** 音は実際に再生したが、Mac はミュートだった。
- **未解決：** 別の書き出しと重なったときの約2分の停止は再現せず、原因はわかっていない。

## 目標にしないこと

- カメラの回転、ブラウザでの 3D 描画。
- 肌だけ、布だけ、金具だけといった部位ごとのつまみ。上の崩れの原因がわかってから考える。それまでは全身と服全体の値で扱い、部位の話は会話で受ける。
- 画質を落として速くする切り替え。効果が薄いため。
- 変化の拍数のつまみ、スポットと環境光を切り替えるつまみ。どちらも会話で変える。
- 配信中の照明の調整、OBS とライブの stage の操作。
- WebRTC などの映像の配信の仕組み。手元のブラウザへ JPEG を送る形で足りている。
- MCP サーバー。

## 失敗とみなすこと

動いていても、次の場合は失敗である。

- ライブの絵と本番の書き出しが、同じ設定と同じコマで見分けられるほど違う。この道具を作る意味がなくなる。
- 人が「このぐらい」を押す前に、AI が設定を書き換える。
- 効かない区間の大きいつまみを渡す。
- 描画側が止まっているのに、絵が動いているように見える。
- 範囲の境が拍からずれる。
- 描画側がないと動画レビューが使えない。

## 守ること

- 個人のモデル、モーション、秘密情報、決め打ちのパスをこのリポジトリに入れない。画面の画像はユーザーの指示どおり実際のキャラクターで撮ってよいが、データと個人のパスは入れない。
- サーバーは `127.0.0.1` でだけ待ち受け、`Host`、`Origin`、起動ごとのトークンを確かめる。
- 依存は MIT、Apache、BSD、MPL に限る。Theatre.js、Triplex、Unity Render Streaming は使わない。どのツールも頼る前に動かして確かめる。
- ダンスの撮影に使っている Unity プロジェクト、配信中の OBS、ライブの stage、Unity のシーンを許可なく変えない。
- コミットとプッシュはユーザーが頼んだときだけ。

## 細かい決定（設計者の判断）

ユーザーとは話していない点で、設計者が決めた。読むときに確かめてほしい。

- **背景のぼけ：** ユーザーの指定がないので、全場面に効かせる側に置く。
- **「だいたい全場面」の例外：** つまみでは扱わず、会話で受ける。範囲は繰り返しの区間でもあるので、範囲を選んだだけで例外になると、サビを繰り返しながら全場面の値を決められない。
- **変化の位置：** 変化は範囲の先頭の拍で変わりきり、末尾の拍で元に戻りきる。拍に着地させるためで、AI と描画側の取り決めなので、会話で変えられる。
- **範囲を繰り返す再生：** ユーザーには想定として伝えただけで、確認は取っていない。
- **調整に使うプロジェクト：** ユーザーの許可で本体に足したので、調整も本体で行う。ダンスの撮影と同時には Editor を開けないので、順番に使う。
- **音と絵のずれ：** 絵は音より約100ms遅れて見える。音を同じだけ遅らせて合わせるかは、実際に聞いて決める。
- **サーバーの中継：** つまみと絵をサーバー経由にする。直接つなぐより少し遅くなるが、トークンの確認を保てる。

## ユーザーの判断が要ること

- **本番の書き出しを `LookLive.Export` に切り替えるか。** 本体を変えることは「別に本体変えていいよ」で許可された。切り替えると、ダンスのセッションが使っている今の書き出しの手順が変わる。

## 作る人に任せること

- `POST /knobs` の細かい形、絵の ID の扱い。
- ライブと動画の切り替えの画面の細部、つまみの見た目。
- 音の再生と描画側の時計のそろえ方。条件は、再生中のずれが広がり続けないこと。
- `settled` の出来事を `review.json` にどう残すか。

## 動いたと言える条件

1. 偽の描画側で、つまみの入れ替え、値の送信、「このぐらい」から `gakuya wait` までを自動テストで通せる。描画側を止めると、応答がないことが画面に出る。
2. 範囲の両端が拍に吸い付くことを、クリック音の合成音で確かめる。
3. 実物の描画側で、同じ設定、同じコマのライブの絵と本番の書き出しを `gakuya` の左右比較で並べ、ユーザーが見分けられない。
4. 実物の描画側で、音を鳴らして拍に合わせた色の変化をユーザーが確かめられる。
5. このセッションの Claude Code を AI 役にして、利用の流れの 1〜6 を実際の曲で通す。
6. リポジトリに個人の素材と決め打ちのパスがない。動画レビューの今のテストがすべて通る。
